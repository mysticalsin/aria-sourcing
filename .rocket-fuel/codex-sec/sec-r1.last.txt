blocker: `scanOutboundForLeaks` is only wired “after compose”, but candidate-bound approval/send paths still only call `gateOutbound`: `src/app/api/outreach/approve/route.ts:54-75`, `src/app/api/outreach/send/route.ts:161-171`, `src/app/api/outreach/whatsapp-review/route.ts:131-139`, `src/lib/dispatch-outbound.ts:223-236`. The invariant is “must NEVER reveal”, so leak checks need to run at every candidate-bound sink, not just WhatsApp compose.

blocker: the design closes the confirmed WhatsApp leak at `src/lib/whatsapp-inbound.ts:196-200`, but it does not cover other model paths that produce candidate-bound drafts: live outreach prompts use reduced role fields in `src/lib/store.ts:2095-2111` and `2336-2350`; `/api/sourcing-agent` uses campaign `jobAnalysis` to draft outreach in `src/app/api/sourcing-agent/route.ts:57-71`; `/api/agents/run` serializes full `campaign.jobAnalysis` into model prompts via `initialState` and `JSON.stringify(state.brief)` at `src/app/api/agents/run/route.ts:129` and `src/lib/agents/graph.ts:121,172-175`. Some are operator-triggered, not candidate-reply surfaces, but their outputs can become candidate-facing.

blocker: the salary fit split is only partially achievable today. WhatsApp can do it if salary is extracted server-side from `spec.role_brief`, withheld from `buildReplyPrompt`, and stored only as an internal assessment. Careers cannot yet meet the owner requirement because public careers input has no target salary field (`src/lib/careers.ts:27-44`) and the chatbox never asks for salary (`src/components/careers/chatbox.tsx:340-377`). Add schema/UI/server storage before claiming this works there.

risk: `detectInjection` regex is a triage signal, not a security boundary. It is easy to bypass with whitespace, punctuation, Unicode confusables, language-switching, base64/rot13, screenshots/CV text, or multi-turn phrasing. Residual risk after whitelist is acceptable only if no internal data reaches the model and candidate text is delimited as untrusted. Do not treat regex coverage counts as proof.

risk: `scanOutboundForLeaks` as designed catches literal salary numbers/tokens, but not inference leaks: “that range should work”, “you are above budget”, “a bit over 100”, “competitive within band”, “we can meet your ask”, or “the upper end is close”. Candidate-facing salary copy should be allowlist-based: either ask for the candidate’s target range, or say a recruiter can discuss compensation. No “in range / above / below / fits budget” phrasing should go back to the candidate.

risk: `DISCLOSABLE_FIELDS` does not match the real `JobAnalysis` shape. The code has `requiredSkills`, `niceToHaveSkills`, `locationType`, `regions`, `employmentType`, etc. (`src/lib/types.ts:165-195`), while the design names `techStack`, `responsibilities`, `workModel`, `jobDescription`. That will either produce thin/empty summaries or encourage ad hoc mapping outside the policy module.

risk: forbidden fields are incomplete. Add at least `currency`, `equity`, `validationWarnings`, `urgency`, `expectedStartDate`, `department` if client-identifying, `hiringManagerEmail`, `reportingTo`, `teamSize`, `sourcingStrategy`, `scoringWeights`, `metrics`, `owner_id`, `workspace_id`, `seat_id`, `flowise_chatflow_id`, recruiter/operator names, client/account names, margin/bill/pay/rate variants, and any other candidate names/PII.

risk: `/api/careers` is currently deterministic and already projects a public-only job shape with no salary (`src/lib/careers.ts:4-17`, `95-138`). The design says “same policy applied to careers chatbot” (`.rocket-fuel/design-agent-security.md:39`), but there is no LLM there today. Either mark careers as “already deterministic, no LLM” or specify the future LLM change.

risk: reply classification sends candidate text to a model (`src/lib/store.ts:2970-2990`) and accepts model `draftResponse` (`src/lib/store.ts:2997-3004`). It does not pass a role brief, so it is not the salary-source leak, but its draft can enter the reply workflow. Candidate-bound leak scanning should cover these drafts before approval/send.

nit: `COMMITMENT_PATTERNS` is private in `src/lib/autopilot.ts:200-207`; “extend the existing gate” will be messy unless the disclosure scan is a shared exported function used by `decideAutopilot`, approval routes, send routes, and WhatsApp review.

nit: make this easy to modify by centralizing two things, not one: `toCandidatePublicRoleContext()` for source minimization, and `validateCandidateBoundText()` for every sink. If every route wires its own salary scan, the next channel will drift.
