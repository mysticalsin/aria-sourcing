## The category shift

Today ARIA is a **faster search box**: recruiter types a query → providers return profiles →
scored → reviewed → drafts. Every role starts from zero, in a browser, on demand.

100x is a different category: a **continuously-operating talent supply engine**.

- Sourcing runs on **durable background jobs**, not on-demand in a tab. The system is always
  discovering, enriching, de-duplicating, and consent-tracking — while nobody is watching.
- A new requisition does not *trigger* a search. It **queries an already-warm person graph**
  and returns a same-day, evidence-backed, ranked shortlist + approval-gated draft outreach.
- Time-to-shortlist collapses from days (source → wait → enrich → review) to **seconds**,
  because the work already happened.

Two moats sit on top — both things LinkedIn Recruiter / Apollo / Gem are business-model-incapable
of copying:

1. **The redeployment flywheel (the Mantu-shaped 100x).** For a consulting/staffing firm the
   highest-margin candidate is one you already placed who is rolling off. Track bench/rolloff
   dates; proactively match rolling-off consultants to open reqs (internal AND external) before
   they hit the bench. Your people, your consent, your data — uncopyable.
2. **Provable-lawful-process as a sales weapon.** Every candidate carries a cryptographically-
   attributable dossier (who sourced, who revealed PII, lawful basis, consent state, non-
   discrimination proof), exportable to a client or DPA. You win EU enterprise deals because you
   can *prove* the process.

The insight from the 4-critic panel: **this is all a data-model problem, not a "more AI" problem.**
The moat is a compounding consented corpus + provable process. Both are half-built.

## Inviolable through every phase (unanimous)

never-auto-send (DB-enforced approval) · RLS multi-tenancy · GDPR erasure 0033 (extend, never
bypass) · LinkedIn assisted-manual policy · consent passports · provenance · discrimination-proxy
filter · deterministic auditable scoring (fix its dead inputs; don't replace with a black box).

### Phase 2 — The pipeline leaves the browser  ("sources while you sleep, safely")
- Server commit RPC `commit_sourced_candidates(workspace_id, expected_updated_at, candidates[])`
  — same optimistic-concurrency + campaign-fingerprint re-check the client does, in-transaction.
- Durable `jobs` table (recurring_search | enrichment_batch | provider_poll) + a long-lived Fly

- Move the enrichment budget ledger server-side into an authority table (reuse the calendar
  claim-ledger pattern). Drafts still stop at the approval gate — automation adds volume, never
  an auto-send path. **L; the Fly worker is owner-gated infra (deploy + secrets).**

### Phase 3 — Person model + the redeployment flywheel
`persons` + `candidate_identities` (canonicalized email/URL) + `candidacies` (person × campaign,
N over time). Dedupe becomes **suggest-don't-block** across campaigns. "Match from Vivier →
assign to campaign" creates a new candidacy for an existing person (re-scored, consent reused).
Add bench/rolloff tracking + proactive rolloff→req matching. This is the flywheel. **L.**

### Phase 4 — Provable compliance as product
Thread `auth.uid()` into every attributable mutation (PII-reveal, outreach-approval, consent-
change ledgers get actor_id/actor_email, forged-proof-resistant via SECURITY DEFINER). Add
`GET /api/compliance/dossier?candidateId|campaignId` → exportable lawful-basis + non-discrimination
+ consent + attribution record. Turns the half-built moat into a sales artifact. **L.**

### Phase 5 — Closed learning loop + semantic match + wider agent reach
- pgvector `embedding` column on the Phase-1 table + HNSW index; "more like this hire" similarity
  search (embed headline + techStack + homed experience/education — now that they're stored).
- Outcome-driven scoring: aggregate reply/interview/hire outcomes → emit bounded, per-campaign,
  human-approved weight-adjustment PROPOSALS through the existing two-person lesson gate. The one
  adaptive edge competitors never see (your placement data).
- Register apollo_search + apify_profile_search as agent tools under the existing receipt/authority
  + discrimination-filter, so the autonomous loop reaches the providers that actually find people.

## Why this order

Phase 0 makes the score honest and the data real (cheap, safe, no gate). Phase 1 is the one
structural unlock everything else needs — but it's the highest-risk migration (GDPR authority is
welded to the blob), so it gets its own written plan, not autopilot. Phases 2-5 each ride the
Phase-1 table and the existing authority spine; several need owner-gated Fly infra. Embeddings and
outcome-learning are deliberately last — they are worthless on a blob and priceless on the table.
