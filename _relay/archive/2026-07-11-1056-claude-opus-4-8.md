## Current state (verifiable facts)

- Live evidence (unrefreshed since the token incident, treat as directional):
  - `https://aria-mantu-app.fly.dev/api/health` → 200 (liveness only).
  - `https://aria-mantu-kong.fly.dev/healthz` → 200.
  - `https://aria-mantu-kong.fly.dev/rest/v1/` → 503 `PGRST002` "Could not query the database".
  - `https://aria-mantu-kong.fly.dev/auth/v1/health` → 503 "name resolution failed".
  - Per shift 24: `aria-mantu-db` and `aria-mantu-auth` machines **exit code 1** (crash-loop).
- Chain of causation (static analysis, HIGH confidence — confirm from logs in step 1):
  - `aria-mantu-db` crash-loops → its Machine is not RUNNING → Fly `.internal`
    6PN DNS only resolves RUNNING machines → siblings can't resolve
    `aria-mantu-db.internal` → Auth logs "name resolution failed", REST logs
    `PGRST002`. **Fix the DB crash and the 503s cascade-clear.**
- **Primary root-cause finding (new this shift):** `fly.db.toml` mounts the
  volume at `destination = "/var/lib/postgresql/data"` (the image's `PGDATA`)
  and **never sets a `PGDATA` subdir**. Every fresh Fly volume ships a
  `lost+found` directory, so `initdb` aborts: *"directory
  '/var/lib/postgresql/data' exists but is not empty ... It contains a
  lost+found directory, perhaps due to it being a mount point."* → container
  exits 1 → crash loop. This is the canonical Fly-Postgres footgun and is fixed
  by pointing `PGDATA` at a **subdirectory** of the mount. `grep PGDATA` across
  all toml/Dockerfile/sh = **not set anywhere.**
- Secondary crash suspects to rule out from logs (do not assume; step 1 picks
  the branch): (H2) `POSTGRES_PASSWORD` secret unset on `aria-mantu-db` → the
  postgres entrypoint refuses to init; (H3) OOM on the 1gb VM during heavy
  supabase/postgres init; (H4) a dirty/half-initialized volume from a prior
  crashed attempt; (H5) a first-init SQL script erroring
  (`docker/db/01-roles.sql` `\set pgpass` backtick expands `$POSTGRES_PASSWORD`
  — empty if the secret is unset).
- **No always-on guarantee on the stateful/backend apps.** `fly.db.toml`,
  `fly.auth.toml`, `fly.rest.toml` have NO `auto_stop_machines` /
  `min_machines_running`. A stateful DB must never auto-stop. (For contrast
  `fly.app.toml` has `auto_stop_machines="suspend"` + `min_machines_running=1`;
  `fly.kong.toml` has `min_machines_running=1`.)
- **No admin user is created anywhere.** `deploy-fly.sh` and
  `e2e-workflow-test.sh` contain zero user-creation. `GOTRUE_DISABLE_SIGNUP=true`
  + `GOTRUE_MAILER_AUTOCONFIRM=true`. The requested admin (credentials supplied through a protected channel) must be minted via the GoTrue **admin**
  API (service_role) after Auth is up — see step 6.
- **Deploy mechanism is currently un-triggerable by design.** The
  `Deploy Aria Mantu (Fly)` workflow is `disabled_manually`; the default branch
  is `vercel-demo` and the workflow file is **absent** there. `workflow_dispatch`
  requires the workflow definition to exist on the default branch. Working branch
  is `deploy/fly-github-actions` @ `05cda61` with uncommitted shared work.
- Repo `mysticalsin/aria-sourcing-demo` is **public** (temporary, for free
  Actions). Tony wants it set **private** again only at the very end.
- `deploy-fly.sh` already orchestrates the correct order (secrets → db →
  bootstrap-migrations → auth+rest → kong+IPs → smoke → app). The runbook below
  reuses its steps; the only code change needed is the config fix in step 2.

### Step 1 — Confirm the DB crash cause from real logs (don't guess)
```
fly logs   -a aria-mantu-db --no-tail | tail -80
fly machine list   -a aria-mantu-db
fly machine status <db-machine-id> -a aria-mantu-db
fly secrets list   -a aria-mantu-db        # POSTGRES_PASSWORD + JWT_SECRET present?
fly volumes list   -a aria-mantu-db
```
Match the log line to the branch:
- Contains `not empty` / `lost+found` / `initdb` → **H1 (expected).** Go to step 2.
- Contains `You must specify POSTGRES_PASSWORD` / `Database is uninitialized` →
  **H2.** The `POSTGRES_PASSWORD` secret is missing on `aria-mantu-db`; set it
  (step 2 secrets) and continue.
- `Out of memory` / `Killed` / signal 9 → **H3.** Bump `fly.db.toml [[vm]]
  memory` to `2gb`, redeploy.
- `PG_VERSION` / `incompatible`/ recovery errors, or the volume already has a
  partial cluster → **H4.** Recreate the volume clean (step 2, optional-D).

### Step 2 — Fix `fly.db.toml` (the core change) and align always-on
Apply this diff to `fly.db.toml`:
```toml
[env]
  POSTGRES_HOST = "/var/run/postgresql"
  POSTGRES_PORT = "5432"
  POSTGRES_DB   = "postgres"
  JWT_EXP       = "3600"
  PGDATA        = "/var/lib/postgresql/data/pgdata"   # <-- ADD: init into a SUBDIR, not the mount root (dodges lost+found)

[[services]]
  internal_port        = 5432
  protocol             = "tcp"
  auto_stop_machines   = "off"    # <-- ADD: a stateful DB must never auto-stop
  auto_start_machines  = false    # <-- ADD
  min_machines_running = 1        # <-- ADD
  [[services.tcp_checks]]
    grace_period = "30s"
    interval     = "15s"
    timeout      = "3s"
```
Do the same always-on trio (`auto_stop_machines="off"`, `auto_start_machines=false`,
`min_machines_running=1`) inside the `[[services]]` block of `fly.auth.toml`
(port 9999) and `fly.rest.toml` (port 3000). Auth/REST are internal-only backends
that must also stay resident.

Ensure the DB secrets exist (H2 guard):
```
fly secrets set -a aria-mantu-db POSTGRES_PASSWORD="$FLY_PG_PASSWORD" JWT_SECRET="$FLY_JWT_SECRET" JWT_EXP=3600
```
**(optional-D — only if step-1 logs showed H4 / a dirty volume; there is NO
production data — DB never booted, no backups exist, safe to wipe):**
```
fly machine destroy <db-machine-id> -a aria-mantu-db --force
fly volumes destroy <vol-id> -a aria-mantu-db --yes
fly volumes create aria_db_data -a aria-mantu-db --region cdg --size 3 --yes
```
(A recreated volume STILL has `lost+found`; the `PGDATA` subdir fix is what
actually resolves it — the recreate only clears a partial cluster.)
