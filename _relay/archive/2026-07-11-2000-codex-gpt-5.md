## Root cause and source recovery

- The pinned Supabase PostgreSQL image cannot initialize when a Fly volume containing lost+found is mounted directly at /var/lib/postgresql/data. A PGDATA-only override also fails because /etc/postgresql/postgresql.conf pins data_directory to that path.
- fly.db.toml now mounts the volume parent at /var/lib/postgresql, retaining the image data directory at the durable child /var/lib/postgresql/data.
- docker/db/entrypoint.fly.sh fails closed on a legacy root-level cluster, unexpected root entries, or a partial child cluster. docker/db/mark-init-complete.sh records the exact aria-db-init-v1 completion marker.
- The exact database image passed clean initialization, two restarts, and container recreation on the same volume without initialization secrets while preserving data and role-specific authentication.
- Owner and migrator authority are split:
  - direct supabase_admin superuser session owns privileged ACL, role rotation, Auth ownership, and JWT policy;
  - direct postgres NOSUPERUSER session owns the numbered migration ledger;
  - Auth uses supabase_auth_admin;
  - REST uses authenticator;
  - all active passwords and the JWT secret must be distinct 43-128 character base64url values;
  - unused privileged login roles are set to NOLOGIN with no password.
- First-init and owner-reconciliation logging suppresses statement text, failed-statement text, and error parameters until secret-bearing work commits. Canary scans found no credential or JWT markers.
- Temporary DB and bootstrap secrets are staged through stdin, retired before runtime acceptance, and verified absent even across ambiguous command failures.
